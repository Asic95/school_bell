# План оптимізації використання оперативної пам’яті

## Поточна ситуація

Під час швидкого переходу між сторінками програма збільшує використання пам’яті. Основні підозрілі місця:

- повторне створення JavaFX-сторінок;
- нескінченний `Timeline` у `EfirStatusCard`;
- фонові задачі, listeners та анімації, які можуть не зупинятися;
- кеш зображень радіостанцій;
- native-пам’ять JavaFX та графічні ресурси;
- окремий процес FFmpeg під час роботи з аудіо.

У попередньому вимірюванні Java heap після `GC.run` займав приблизно 41 МБ, тоді як увесь процес Java займав понад 500 МБ. Тому потрібно окремо розглядати Java heap і native-пам’ять процесу.

## 1. Контроль життєвого циклу UI

Перевірити всі компоненти, які створюють довгоживучі об’єкти:

- `Timeline`;
- `FadeTransition` та інші анімації;
- listeners;
- фонові `Thread`;
- `ScheduledExecutorService`;
- WebSocket або інші мережеві з’єднання.

Для таких компонентів додати явні методи `stop()` або `dispose()` і викликати їх, коли сторінка чи діалог більше не використовується.

Особлива увага — `EfirStatusCard`, де раніше кожне створення картки запускало нескінченний `Timeline`.

## 2. Не створювати сторінки заново

Основні сторінки краще створювати один раз і повторно використовувати.

Потрібно перевірити, щоб після кешування сторінок дані не ставали застарілими. Після змін у розкладі, школі або налаштуваннях відповідна сторінка повинна мати метод `refresh()`.

Редакторські екрани можна залишати динамічними, якщо вони мають власний тимчасовий стан.

## 3. Профілювання пам’яті — основні сценарії перевірено

Під час перевірки використовувалися:

```powershell
jcmd <PID> GC.run
jcmd <PID> GC.heap_info
jcmd <PID> GC.class_histogram
jcmd <PID> VM.native_memory summary
```

Команда `VM.native_memory summary` не спрацювала, оскільки поточна JVM була запущена без параметра:

```text
-XX:NativeMemoryTracking=summary
```

Тому Java heap і Metaspace вдалося виміряти точно, а native-пам’ять оцінювалася через `WorkingSet` і `PrivateMemorySize` Windows. Для повного поділу native-пам’яті JavaFX, Prism і JVM потрібен окремий запуск із Native Memory Tracking.

### Чистий запуск

Після перезапуску програми без переходів між сторінками, без радіо та без трансляції:

- Working Set: приблизно `250 МБ`;
- Private Memory: приблизно `367 МБ`;
- Java heap: приблизно `27 МБ`;
- Metaspace: приблизно `34 МБ`.

Це базове споживання самої JavaFX-програми та JVM.

### Навігація по сторінках

Після переходів між основними сторінками та виконання `GC.run` Java heap залишався в межах приблизно `27–40 МБ`. Це означає, що великого накопичення Java-об’єктів після GC не виявлено.

Найпомітніші зміни:

- «Тижневий розклад» дав приблизно `+56 МБ` Working Set після GC;
- «Час дзвінків» дав приблизно `+40 МБ` Working Set;
- «Предмети» дали найбільший одноразовий приріст — приблизно `+46 МБ` Working Set;
- «Системні налаштування» дали приблизно `+33 МБ` Working Set;
- «Аудиторії» дали приблизно `+14 МБ`;
- «Заміни та зміни», «Сповіщення», «Класи» та «Імпорт даних» не дали значного приросту після GC;
- «Керування ефіром» після кешування сторінки практично не збільшило пам’ять.

Для сторінок із найбільшим приростом Java heap після GC повертався до невеликих значень. Це вказує переважно на native-графіку JavaFX, CSS/layout-кеші та внутрішні резерви JVM, а не на постійний Java memory leak.

### Аудіо та FFmpeg

Під час двох хвилин роботи радіо окремий процес FFmpeg мав приблизно:

- Working Set: `21 МБ`;
- Private Memory: `19 МБ`.

Після вимкнення радіо процес `ffmpeg-amd64-3.3.1.exe` зник. Ознак накопичення FFmpeg-процесів не виявлено.

### WebSocket-трансляція

Після двох хвилин трансляції з двома активними клієнтами:

- до GC Java heap зріс приблизно до `71 МБ` через тимчасові dashboard-дані та JSON;
- після GC heap повернувся приблизно до `39 МБ`;
- Working Set становив приблизно `432 МБ`;
- окремих процесів FFmpeg не було.

Це підтверджує, що dashboard-дані та JSON створюють тимчасове навантаження на GC, але не накопичуються як постійний витік.

### Загальний висновок

Основний приріст пам’яті відбувається під час першого створення складних JavaFX-сторінок. Після `GC.run` Java heap не демонструє постійного зростання. Значна частина показників Task Manager припадає на native-пам’ять JavaFX/JVM, яку звичайний `GC.run` не зобов’язаний повертати Windows.

Найважливіші практичні висновки:

- кешування основних сторінок було правильним рішенням;
- `EfirStatusCard` більше не накопичується при навігації;
- FFmpeg-процеси завершуються коректно;
- WebSocket-трансляція не показала витоку Java heap;
- сторінка «Предмети» є найважчою за native-приростом і заслуговує окремого повторного тесту;
- для повного аналізу JavaFX/native memory потрібен повторний запуск із `-XX:NativeMemoryTracking=summary`.

## 4. Перевірити діалоги — низький пріоритет

Пункт переглянуто. Критичного постійного витоку в основних діалогах не виявлено:

- вибір радіостанції зупиняє preview-аудіо при закритті;
- медіа-контроль зупиняє свій `Timeline` у `setOnHidden`;
- listeners редакторів прив’язані до контролів самого діалогу;
- Toast-анімації самостійно видаляють повідомлення після завершення.

Можливі дрібні покращення, але вони не є основною причиною зростання пам’яті:

- очищати `imageCache` у `RadioSelectionDialog` при закритті;
- захистити `MediaQuickControlDialog` від повторного створення `Timeline`;
- додати скасування великого PDF-імпорту при виході зі сторінки;
- обмежити кількість одночасних Toast-повідомлень.

Першочергово цей пункт можна не змінювати.

## 5. Обмежити кеш зображень — перевірено, низький пріоритет

У `RadioSelectionDialog` є локальний `imageCache`, але він належить конкретному діалогу й не є глобальним кешем. При закритті діалогу він має стати доступним для GC разом із самим діалогом.

Також зображення завантажуються лише для видимих станцій і масштабуються до `48x48`, тому кеш не є основною причиною довготривалого зростання пам’яті.

Висновок: постійного витоку в цьому місці не виявлено. За бажанням можна додати `imageCache.clear()` у `setOnHidden` або встановити ліміт кількості елементів, але це необов’язкове дрібне покращення.

## 6. Перевірити JavaFX-кеші та зображення — перевірено, низький пріоритет

JavaFX-кеш використовується лише в кількох місцях для карток, кнопок і `EfirStatusCard`. Великих PNG або інших великих локальних ресурсів не знайдено. Основна іконка програми має розмір приблизно 7 КБ, а favicon радіостанцій масштабуються до `48x48`.

Зайвого постійного створення `ImageView` не виявлено. Графічний кеш може бути зайвим для деяких статичних карток, але він не пояснює зростання пам’яті на сотні мегабайт і не виглядає джерелом витоку.

Висновок: пункт перевірено, критичних проблем немає. За бажанням можна пізніше порівняти продуктивність після вимкнення кешу для статичних карток, але це низький пріоритет.

## 7. Оптимізувати broadcast-оновлення — базову оптимізацію виконано

Було перевірено щосекундне оновлення Dashboard і WebSocket-трансляцію.

Виконано:

- додано перевірку наявності підключених WebSocket-клієнтів перед формуванням dashboard-даних;
- без клієнтів не створюються зайві `Map`, списки статусів і тимчасові об’єкти;
- без клієнтів не виконується JSON-серіалізація;
- якщо трансляція увімкнена, але телевізорів або браузерів немає, `getScheduleForClass()` не викликається щосекунди;
- для підключених клієнтів логіка трансляції та формат даних не змінені.

Тимчасові `Map` і JSON не є постійним витоком пам’яті, але створюють навантаження на GC, коли трансляція реально використовується.

Теоретичні подальші оптимізації:

- змінити частоту трансляції з 1 до 2 секунд;
- кешувати розклад класів і не виконувати `getScheduleForClass()` щосекунди;
- розділити незмінні та динамічні дані Dashboard;
- формувати повний JSON лише після зміни розкладу, а countdown оновлювати окремо.

Ці зміни можуть зменшити CPU, кількість звернень до бази та навантаження на GC, але є складнішими й можуть вплинути на актуальність даних трансляції. На поточному етапі вони не є обов’язковими.

## 8. Перевірити аудіо та FFmpeg — перевірено

FFmpeg працює окремим процесом, тому його пам’ять перевірялася окремо.

За результатами перевірки коду:

- `AudioInputStream` закривається через `try-with-resources`;
- `SourceDataLine` закривається через `try-with-resources`;
- тимчасові WAV-файли видаляються після завершення відтворення;
- FFmpeg-процес завершується через `destroyForcibly()` у `finally`.

Практичний тест: після приблизно 20 хвилин прослуховування музики та зупинки аудіо команда `Get-Process ffmpeg` не показала жодного активного процесу.

Висновок: ознак накопичення `ffmpeg.exe` або постійного витоку в аудіопідсистемі не виявлено. Швидке перемикання між багатьма радіостанціями можна перевірити окремо як крайовий сценарій, але це не є поточною проблемою.

## 9. Не починати з налаштування Garbage Collector

Заміна G1 GC, зміна `-Xmx` або перехід на новішу Java не звільнить об’єкти, які утримуються listeners, timers або JavaFX-компонентами.

Спочатку потрібно знайти джерело утримання пам’яті, а вже потім оптимізувати JVM.

## Рекомендований порядок роботи

1. Перевірити результат кешування основних сторінок.
2. Перевірити, чи зупиняються всі `Timeline` та анімації.
3. Повторити тест швидкої навігації.
4. Виконати `jcmd <PID> GC.run` і `GC.heap_info`.
5. Перевірити кеш радіо-зображень.
6. Перевірити FFmpeg і діалоги.
7. За потреби увімкнути Native Memory Tracking.
8. Лише після цього розглядати налаштування JVM та Garbage Collector.

## Орієнтовні критерії

- до 500–650 МБ у Task Manager після активної навігації — прийнятно;
- 650–800 МБ, якщо пам’ять стабілізується, — потребує спостереження;
- постійне зростання понад 800 МБ–1 ГБ — підозра на витік;
- після `GC.run` Java heap має суттєво зменшуватися, якщо об’єкти не утримуються активними посиланнями.

## 10. Чи варто переписувати програму на Go

Перехід на Go теоретично може зменшити базове споживання пам’яті, оскільки зникають JVM і JavaFX. Проте це не гарантує пропорційного зменшення Working Set.

Основне споживання програми пов’язане не лише з Java heap, а й із графічним toolkit, native-пам’яттю, текстурами, шрифтами, CSS/layout-кешами та внутрішніми резервами runtime. У Go ці ресурси все одно будуть потрібні конкретному UI-фреймворку.

Особливі ризики:

- Go + WebView може використовувати стільки ж або більше пам’яті через Chromium/WebView;
- Go + Fyne/Gio може мати менший baseline, але це потрібно перевіряти на прототипі;
- власний Win32 UI потенційно буде економнішим, але вимагатиме фактичного переписування всієї UI-архітектури;
- FFmpeg працює окремим процесом і майже не залежить від вибору Java чи Go.

Поточні вимірювання не показують класичного постійного Java-heap leak: після `GC.run` heap повертається приблизно до 27–40 МБ. Тому повне переписування на Go не є першочерговим рішенням проблеми пам’яті.

Перед можливим переписуванням потрібно було б зробити прототип одного найважчого екрана, наприклад «Предмети», і порівняти його з JavaFX за однаковим сценарієм роботи.

## 11. Оновлення Java та JavaFX

Поточний проєкт використовує Java source/target `21` і JavaFX `21`.

Оновлення JavaFX до новішої версії може дати:

- виправлення відомих витоків і помилок у JavaFX-контролах;
- кращу стабільність `TableView`, `TreeView`, `ListView` та графічного pipeline;
- покращення сумісності, продуктивності й безпеки;
- потенційно менше native memory у конкретних сценаріях.

Однак нові версії не гарантують суттєвого зменшення споживання пам’яті, якщо сторінки, listeners, timers або JavaFX Node-и продовжують утримуватися програмою.

JavaFX 27 потребує JDK 25 або новішої версії. Для стабільного продукту доцільно спочатку розглянути LTS-комбінацію Java 25 + JavaFX 25. Java 27 + JavaFX 27 можна використовувати для окремого порівняльного тесту, але це не слід розглядати як гарантовану оптимізацію пам’яті.

Порівняння версій потрібно виконувати на однаковій збірці сценарію:

1. чистий запуск;
2. однакова послідовність переходів між сторінками;
3. однаковий час роботи WebSocket і Dashboard;
4. `jcmd <PID> GC.run`;
5. вимірювання Java heap, Working Set і Private Memory.

## 12. Очищення неактивних сторінок

Поточний `AppNavigation` кешує основні сторінки в полях `dashboardNode`, `scheduleNode`, `notificationsNode`, `efirNode`, `schoolNode`, `importNode` та `systemNode`. Це запобігає повторному створенню UI, але водночас утримує всі Node-дерева в пам’яті протягом усього запуску програми.

Можна додати політику очищення сторінок, які не використовувалися, наприклад, 25 хвилин:

1. зберігати час останнього відкриття кожної сторінки;
2. періодично перевіряти час неактивності;
3. не очищати активну сторінку;
4. перед очищенням викликати `dispose()` для timers, animations, listeners, subscriptions і мережевих ресурсів;
5. видалити Node з `contentArea`;
6. обнулити посилання на Node та внутрішній `builtView`;
7. під час наступного відкриття побудувати сторінку заново.

Самого `contentArea.getChildren().clear()` недостатньо. Якщо `AppNavigation`, `MainApp` або сам View-клас продовжують зберігати посилання на Node, його об’єкти й native-ресурси не стануть доступними для GC.

Для цього View-класи мають мати повний життєвий цикл `build()` / `refresh()` / `dispose()` / `reset()`. Особливо це стосується `EfirView`, де потрібно зупиняти статусні компоненти, таймери, listeners і мережеві ресурси.

Не слід автоматично очищати:

- активну сторінку;
- сторінку з незбереженими змінами;
- відкриті діалоги та редактори;
- Dashboard, якщо він використовується для постійного оновлення даних або трансляції.

Практичніше використовувати кеш із максимумом 2–3 важких сторінок і очищати неактивні сторінки після 25 хвилин. Маленькі сторінки можна залишати закешованими.

## 13. Очікуваний ефект очищення сторінок

У попередніх вимірюваннях окремі сторінки давали приблизний приріст Working Set:

- «Тижневий розклад» — близько 56 МБ;
- «Час дзвінків» — близько 40 МБ;
- «Предмети» — близько 46 МБ;
- «Системні налаштування» — близько 33 МБ.

Ці значення не можна просто скласти: частина пам’яті є спільною для JavaFX, JVM, CSS, шрифтів і графічного pipeline.

Орієнтовний можливий ефект:

- легка сторінка — приблизно 5–20 МБ;
- середня сторінка — приблизно 20–50 МБ;
- складна сторінка — приблизно 40–100 МБ;
- кілька коректно очищених сторінок — потенційно 80–200 МБ.

Наприклад, після активної навігації процес може зменшитися з приблизно 550 МБ до 350–450 МБ. У сприятливому сценарії він може наблизитися до 300 МБ.

Це лише теоретична оцінка. Java heap після `GC.run` може зменшитися значно, але Working Set і Private Memory Windows можуть зменшитися частково, оскільки JVM та JavaFX можуть залишати native-блоки для повторного використання.

Головний очікуваний результат — не обов’язково миттєве повернення всієї пам’яті Windows, а припинення подальшого накопичення після тривалої навігації. Після реалізації потрібно повторити один і той самий тест навігації з очищенням і без нього.
