# Аналіз переходу SchoolBell з Java на Go

## Короткий висновок

Повний перехід SchoolBell з Java на Go зараз виглядає недоцільним.

Go майже напевно зменшить розмір частини програми, але не настільки, щоб це саме по собі виправдало повний rewrite. Поточний застосунок має багато UI-логіки на JavaFX, роботу з аудіо, USB HID-реле, Shelly, SQLite, PDF-імпорт, WebSocket/HTTP-сервери, автооновлення і досить багато готових екранів. Перенесення цього всього на Go буде великим проєктом з високим ризиком регресій.

Практично: краще зараз залишатися на Java і оптимізувати пакування/залежності. Go варто розглядати тільки якщо буде чітка нова ціль: радикально простіший UI, сервісна архітектура, веб-інтерфейс або повний перезапуск продукту.

## Чому інсталятор зараз великий

Розмір близько 230 MB, ймовірно, формується не тільки через Java як мову.

Основні джерела розміру:

- вбудований Java runtime для запуску на комп'ютері без встановленої Java;
- JavaFX runtime;
- FFmpeg native binaries через `jave-nativebin-win64`;
- PDF stack через `tabula` і його залежності;
- SQLite JDBC native частина;
- ресурси, іконки, packaging-обгортка інсталятора.

Навіть якщо перейти на Go, частина важких речей нікуди не зникне:

- FFmpeg все одно потрібен для MP3/радіо/транскодування або треба буде замінити аудіо-рушій;
- PDF-імпорт все одно потребуватиме окремої бібліотеки або зовнішнього інструменту;
- нормальний desktop UI у Go теж має свою вагу або залежність від WebView/runtime.

## Що Go реально може дати

### Менший binary

Go добре збирається в один `.exe`. Для сервісної або консольної програми це може бути умовно 10-30 MB.

Але SchoolBell - не консольна утиліта. Це desktop-застосунок з багатим UI, таблицями, діалогами, графікою, системним треєм, автооновленням, аудіо і обладнанням. Якщо робити UI на Go, реальний розмір буде залежати від фреймворку:

- Fyne/Gio: потенційно компактніше за JavaFX, але UI доведеться переписати повністю і він може виглядати простіше.
- Wails: UI на HTML/CSS/JS + Go backend; зручно, але це вже інша архітектура.
- WebView: може бути компактно, якщо покладатися на встановлений Microsoft Edge WebView2, але треба враховувати його наявність на цільових ПК.

### Просте розгортання backend-логіки

Go добре підходить для:

- HTTP/WebSocket серверів;
- роботи з мережею;
- системних служб;
- невеликих фонових агентів;
- статично зібраних утиліт;
- стабільного запуску без JVM.

Для SchoolBell це могло б бути корисно, якщо колись винести частину логіки в окремий сервіс: наприклад, керування реле, локальний API, broadcast-сервер або updater.

### Швидкий старт

Go-застосунки зазвичай стартують швидко. JavaFX теж може стартувати нормально, але JVM + JavaFX дають більший runtime footprint.

Це плюс Go, але для SchoolBell не виглядає критичним, бо програма працює довго у фоні, а не запускається щохвилини.

## Мінуси переходу для SchoolBell

### Повний rewrite UI

Поточний UI майже повністю написаний на JavaFX:

- Dashboard;
- розклад;
- заміни;
- школа/класи/вчителі;
- налаштування сигналів;
- медіапланувальник;
- радіо;
- оновлення;
- діалоги;
- кастомні картки, стилі, іконки, анімації.

У Go це не переноситься автоматично. Це фактично повторна розробка інтерфейсу.

### Ризик втратити стабільність у критичних сценаріях

SchoolBell керує реальними дзвінками і сигналами:

- перерви;
- уроки;
- повітряна тривога;
- надзвичайна ситуація;
- USB-реле;
- Shelly-реле;
- аудіооголошення;
- автоматичний розклад.

Після rewrite потрібно заново перевіряти всі сценарії. Найбільший ризик не в тому, що щось не скомпілюється, а в тому, що в реальній школі щось спрацює не в той момент або не спрацює взагалі.

### Аудіо може стати складнішим

У Java зараз уже є власний PCM-based `AudioService`, fade-in/fade-out, робота з FFmpeg pipe, MP3 через транскодування, радіопотоки.

У Go це доведеться збирати заново:

- вибір аудіопристрою;
- PCM playback;
- software volume;
- fade;
- MP3/stream decoding;
- стабільна робота з Windows audio;
- правильна зупинка потоків.

Це можливо, але це не маленька заміна.

### PDF-імпорт може бути гіршим

У Java використовується `tabula`, що підходить для PDF table extraction. У Go PDF-парсинг існує, але якість витягування таблиць може бути слабшою або потребувати зовнішніх інструментів.

Якщо імпорт PDF важливий, це окремий ризик.

### HID/USB-реле треба буде перевіряти заново

У Java зараз використовується `hid4java`. У Go є HID-бібліотеки, але поведінку на Windows треба тестувати з конкретним реле:

- reconnect після відключення;
- права доступу;
- feature reports;
- legacy write fallback;
- поведінка після sleep/wake;
- робота на різних ПК.

Це не неможливо, але це hardware-ризик.

### Auto-update доведеться переписати

Поточний механізм оновлення, manifest, завантаження інсталятора, GitHub Releases, UI діалог оновлення - усе це треба буде повторити.

Go може тут бути зручним, але це знову повна міграція логіки.

## Плюси залишитись на Java

- Поточна програма вже працює.
- Більшість складних сценаріїв уже реалізована.
- JavaFX добре підходить для desktop UI.
- SQLite, PDF, WebSocket, HTTP, HID, mDNS вже інтегровані.
- Нові патчі можна випускати швидко.
- Ризик регресій значно менший, ніж при rewrite.
- Поточний розмір інсталятора не є критичною проблемою для GitHub Releases.

## Що можна оптимізувати без переходу на Go

### Перевірити jlink/jpackage

Можна спробувати зробити кастомний runtime тільки з потрібними Java-модулями. Це може зменшити розмір порівняно з повним runtime.

Але треба тестувати, бо JavaFX, SQLite, Tabula і FFmpeg можуть тягнути нативні частини.

### Перевірити, що саме входить в installer

Варто подивитися breakdown розміру:

- runtime;
- app jar;
- FFmpeg binaries;
- installer overhead;
- дублікати;
- тимчасові або зайві файли в packaging input.

Можливо, частину 230 MB можна зменшити без зміни мови.

### Розглянути optional PDF/FFmpeg

Якщо якісь важкі компоненти не потрібні всім користувачам, теоретично їх можна зробити optional. Але для твоєї програми FFmpeg уже став важливою частиною аудіо, тому його прибирати ризиковано.

### Робити нормальні patch-релізи

230 MB для GitHub Release asset - це нормально. Немає потреби переписувати застосунок тільки через розмір релізу.

## Коли перехід на Go мав би сенс

Go варто серйозно розглядати, якщо виконується хоча б кілька пунктів:

- хочеш повністю переробити UI;
- хочеш перейти на web-based інтерфейс;
- хочеш мати окремий background service, який працює без відкритого desktop UI;
- хочеш управляти дзвінками через браузер з інших пристроїв;
- хочеш розділити систему на `SchoolBell Service` + `SchoolBell Admin UI`;
- готовий витратити час на повне тестування реле, аудіо, розкладу і оновлень.

У такій архітектурі Go міг би бути корисним для backend/service частини, а UI можна було б робити окремо.

## Можлива гібридна стратегія

Найрозумніший шлях, якщо дуже хочеться використати Go:

1. Залишити поточний JavaFX-застосунок як основний.
2. Не переписувати все одразу.
3. Винести в Go тільки маленький окремий компонент, якщо з'явиться чітка причина.

Наприклад:

- окремий updater;
- окремий relay-agent;
- окремий локальний HTTP API;
- окрема діагностична утиліта для USB-реле.

Так можна отримати користь від Go без ризику зламати всю програму.

## Попередня оцінка вартості переходу

Орієнтовно:

- UI rewrite: високий обсяг.
- Audio rewrite: високий ризик.
- Relay rewrite: середній ризик, але потрібне тестування на реальному пристрої.
- SQLite/domain logic: середній обсяг.
- PDF import: середній/високий ризик.
- Auto-update: середній обсяг.
- Packaging: середній обсяг.
- Повне тестування: високий обсяг.

Це не виглядає як "переписати за кілька днів". Це окремий великий етап розробки.

## Рекомендація

Для поточного стану SchoolBell я б не переходив повністю на Go.

Краще:

1. Продовжувати Java-версію.
2. Випускати patch-релізи через GitHub Releases.
3. Оптимізувати installer тільки якщо розмір реально стане проблемою.
4. Окремо дослідити jlink/jpackage і склад installer.
5. Go розглядати тільки для окремих сервісних компонентів або для майбутнього повного перезапуску архітектури.

Головна причина: розмір інсталятора - це незручність, але rewrite на Go - це великий технічний ризик для програми, яка керує реальними шкільними сигналами.
