# Технічний аналіз та план оновлення: Модуль синхронізації часу (NtpService)

## 1. Опис проблеми (Problem Summary)

### Симптом
Користувачі повідомляють, що час у додатку **School Bell** відстає (або поспішає) на кілька хвилин від годинника операційної системи Windows (у треї).

### Першопричина (Root Cause)
У поточній версії програми синхронізація часу через NTP ([`NtpService.java`](file:///C:/school_bell/untitled/src/main/java/com/schoolbell/service/NtpService.java)) виконується **лише один раз — при старті програми**. 
Розрахований зсув (`timeOffsetMs`) зберігається як статична константа на весь час роботи програми і беззастережно додається до системного часу:

```java
public LocalTime getCorrectedTime() {
    LocalTime now = LocalTime.now();
    if (isSynced && timeOffsetMs != 0) {
        return now.plusNanos(timeOffsetMs * 1_000_000L);
    }
    return now;
}
```

Якщо користувач (або фонова служба Windows `w32time`) змінює/синхронізує системний годинник комп'ютера під час роботи програми, `timeOffsetMs` **не скидається і не перераховується**.

## 2. Покроковий сценарій виникнення збою

### Приклад з відставанням часу (повідомлення користувача):
1. **Початковий стан:** Системний годинник Windows поспішає на 2 хвилини відносно еталонного світового часу:
   - Час Windows: `12:02:00`
   - Реальний світовий час (NTP): `12:00:00`
2. **Запуск програми:**
   - [`MainApp.java`](file:///C:/school_bell/untitled/src/main/java/com/schoolbell/MainApp.java) викликає `ntpService.startAsyncSync(...)`.
   - Сервер повертає зсув: `offset = NTP - System = 12:00:00 - 12:02:00 = -120 000 мс (-2 хвилини)`.
   - В пам'яті фіксується: `timeOffsetMs = -120 000`.
   - Програма відображає: `12:02:00 + (-2 хв) = 12:00:00` (вірно).
3. **Дії користувача або Windows:**
   - Користувач бачить різницю між годинником Windows (`12:02`) та програмою (`12:00`).
   - Користувач відкриває *Параметри Windows → Час та мова → Синхронізувати зараз* (або служба часу Windows сама проводить автосинхронізацію).
   - Годинник Windows встановлюється в точний час: `12:00:00`.
4. **Критична помилка:**
   - Програма продовжує працювати зі старим зсувом `timeOffsetMs = -120 000 мс`.
   - `LocalTime.now()` тепер повертає `12:00:00`.
   - Розрахунок у програмі: `12:00:00 + (-2 хвилини) = 11:58:00`.
   - **Результат:** Час програми відстає від часу Windows на 2 хвилини! Усі дзвінки пролунають із запізненням на 2 хвилини.

## 3. Супутні вразливості поточної реалізації

1. **Одноразовий запуск (No Periodic Sync):**
   Шкільні комп'ютери працюють тижнями без перезавантаження. Кварцові резонатори материнських плат дрейфують на секунди/хвилини, а статичний зсув не враховує цей дрейф.
2. **Відсутність детекції стрибка часу (No Clock Skew/Jump Detection):**
   Програма не відстежує, чи змінився системний час раптово (через підведення годинника користувачем чи перехід на літній/зимовий час).
3. **Відсутність ручного керування в UI:**
   Користувач не може натиснути кнопку «Оновити час» або переглянути деталі синхронізації на дашборді.
4. **Відсутність можливості відключити NTP:**
   Якщо шкільна мережа працює в закритому домені Active Directory з власним NTP-сервером або якщо порт UDP 123 заблоковано провайдером/фаєрволом, немає налаштування для повного переходу на чистий системний час ОС.
5. **Проблема опівночі (Midnight Wrap-around):**
   `LocalTime.now().plusNanos(...)` переходить через `00:00`, але `LocalDate.now()` у планувальнику [`MainApp.java`](file:///C:/school_bell/untitled/src/main/java/com/schoolbell/MainApp.java#L294) залишається незмінним, що може призводити до розсинхронізації поточної дати навколо опівночі.

## 5. Архітектурний приклад вирішення

### Приклад детекції стрибка часу в `NtpService`:

```java
private long lastSystemTime = System.currentTimeMillis();
private long lastNanoTime = System.nanoTime();

public void checkClockDiscontinuity() {
    long currentSystemTime = System.currentTimeMillis();
    long currentNanoTime = System.nanoTime();
    
    long elapsedSystemMs = currentSystemTime - lastSystemTime;
    long elapsedNanoMs = (currentNanoTime - lastNanoTime) / 1_000_000L;
    
    // Якщо системний годинник зрушився відносно монотонного більш ніж на 3 секунди
    if (Math.abs(elapsedSystemMs - elapsedNanoMs) > 3000) {
        logger.warn("Виявлено стрибок системного часу Windows (дельта: {} мс). Скидання старого NTP-зсуву...", 
            elapsedSystemMs - elapsedNanoMs);
        this.timeOffsetMs = 0;
        this.isSynced = false;
        startAsyncSync(null); // Негайний повторний запит
    }
    
    lastSystemTime = currentSystemTime;
    lastNanoTime = currentNanoTime;
}
```

## 7. Думка ChatGPT Codex: рекомендована модель роботи часу

Поточний план правильно визначає головну причину збою: програма один раз отримує NTP-зсув при старті, зберігає його в `timeOffsetMs`, а потім безумовно додає цей старий зсув до системного часу Windows. Якщо Windows синхронізувався або користувач змінив годинник під час роботи програми, виникає ефект "подвійного зсуву", і дзвінки можуть спрацьовувати із запізненням або завчасно.

Моє бачення: для шкільної системи дзвінків базовим джерелом часу має бути **системний час Windows**, а NTP краще використовувати як **контроль точності та опційну корекцію**, а не як приховану автоматичну заміну системного годинника. Причина практична: користувач дивиться на годинник у треї Windows і очікує, що програма дзвонить саме за ним. Якщо додаток показує інший час, це створює недовіру, навіть якщо NTP-час формально точніший.

### Рекомендований режим за замовчуванням

1. **За замовчуванням використовувати `LocalDateTime.now()` без NTP-корекції.**
   - Дзвінки, дата, оголошення, трансляція та dashboard мають жити в одному часовому джерелі.
   - Це усуває найнебезпечніший сценарій, коли програма й Windows показують різний час.

2. **NTP використовувати для діагностики.**
   - Раз на 30-60 хвилин перевіряти різницю між Windows і NTP.
   - Якщо різниця мала, показувати "Час Windows перевірено".
   - Якщо різниця суттєва, показувати попередження: "Годинник Windows відрізняється від еталонного на X сек/хв".

3. **Автоматичну NTP-корекцію зробити окремим налаштуванням.**
   - Назва: "Коригувати час програми через NTP".
   - За замовчуванням вимкнено.
   - Якщо ввімкнено, UI має явно показувати, що дзвінки працюють за скоригованим NTP-часом, а не напряму за Windows.

### Якщо автоматична NTP-корекція залишається

Тоді її треба зробити не через розрізнений `LocalTime`, а через єдиний сервіс часу:

```java
public final class AppTimeService {
    public LocalDateTime now() { ... }
    public LocalDate today() { return now().toLocalDate(); }
    public LocalTime currentTime() { return now().toLocalTime(); }
}
```

Важливо, щоб scheduler, dashboard, оголошення і broadcast отримували дату і час з одного corrected `LocalDateTime`. Поточна схема, де `LocalTime` коригується через NTP, а `LocalDate.now()` береться напряму з Windows, може давати помилки біля опівночі.

### Захисти, які варто додати в `NtpService`

1. **Один фоновий executor замість нового Thread на кожний запит.**
   - Використати `ScheduledExecutorService`.
   - Додати `AtomicBoolean syncInProgress`, щоб кнопка ручної синхронізації, періодичний sync і detector не запускали кілька NTP-запитів одночасно.

2. **Детектор стрибка системного часу.**
   - Порівнювати `System.currentTimeMillis()` із монотонним `System.nanoTime()`.
   - Якщо різниця більша за 3-5 секунд, скидати старий offset і негайно запускати повторну перевірку.
   - На час перевірки показувати статус "Перевірка часу...", а не мовчки працювати зі старим зсувом.

3. **Безпечна політика offset.**
   - До 500 мс: вважати offset нульовим.
   - 500 мс - 5 сек: можна застосовувати без попередження, якщо ввімкнена NTP-корекція.
   - 5 сек - 5 хв: застосовувати, але показувати помітний статус.
   - Понад 5 хв: не застосовувати автоматично без явного налаштування або підтвердження, бо це може бути неправильний часовий пояс, збій BIOS/RTC або некоректний NTP-сервер.

4. **Не втрачати останню діагностику.**
   - Зберігати `lastSuccessfulSyncAt`, `currentServer`, `offsetMs`, `lastError`.
   - У tooltip показувати не лише сервер і зсув, а й час останньої успішної перевірки.

### Рекомендована пріоритетність впровадження

1. **Найперше:** прибрати ризик "подвійного зсуву" після зміни часу Windows.
2. **Друге:** перейти з `getCorrectedTime()` на єдиний `getCorrectedDateTime()` / `AppTimeService.now()`.
3. **Третє:** додати періодичну перевірку NTP і detector стрибків.
4. **Четверте:** додати UI-статус, ручну кнопку "оновити час" і налаштування NTP.

### Практичний висновок

Найстабільніша модель для School Bell: **Windows-час керує дзвінками, NTP контролює точність і попереджає про проблему**. Автоматична NTP-корекція може існувати, але лише як прозорий режим з окремим налаштуванням, єдиним джерелом `LocalDateTime`, захистом від паралельних sync-запитів і детекцією стрибків системного годинника.

## 8. Думка Antigravity: монотонний якір як корінне вирішення

Обидва попередні підходи — оригінальний план (секції 4–5) і рекомендація Codex (секція 7) — правильно описують симптоми і пропонують розумні пом'якшення. Але жоден не усуває фундаментальну архітектурну причину нестабільності.

### В чому корінь проблеми (іншими словами)

Поточна формула в [`NtpService.getCorrectedTime()`](file:///C:/school_bell/untitled/src/main/java/com/schoolbell/service/NtpService.java#L100-L106):

```
Час програми = LocalTime.now() + timeOffsetMs
             = (годинник Windows)  +  (різниця, яку обчислили один раз)
```

Ця формула **математично нестійка**: вона складає дві величини, одна з яких (годинник Windows) може змінюватись ззовні в будь-який момент, а друга (`timeOffsetMs`) — ні. Будь-яка зовнішня зміна Windows-часу автоматично робить результат хибним.

**Codex пропонує:** детектувати цю зміну і реагувати на неї (нова синхронізація, скидання зсуву).  
**Мій аргумент:** набагато надійніше — архітектурно **унеможливити** вплив Windows-годинника на вже отриману NTP-правду.

---

### Монотонний якір (Monotonic Anchor)

У Java існують **два принципово різних таймери**:

| Властивість | `System.currentTimeMillis()` / `LocalTime.now()` | `System.nanoTime()` |
|---|---|---|
| Що вимірює | Поточну дату/час (wall clock) | Кількість наносекунд від деякого довільного початку |
| Реагує на зміну часу Windows | **Так — стрибає разом із годинником ОС** | **Ні — монотонний, ніколи не стрибає** |
| Придатний для "який зараз час?" | Так | Ні |
| Придатний для "скільки часу пройшло?" | Ні | **Так** |

**Ідея:** NTP дає нам одну правильну точку відліку (`Instant`). Далі ми більше не питаємо Windows "котра година?" — ми самі рахуємо **скільки наносекунд пройшло** від тієї правильної точки через `System.nanoTime()`.

```
Час програми = ntpAnchor + elapsed_nanoTime
             = (правда з NTP в момент синхронізації) + (скільки наносекунд минуло після)
```

У цій формулі **немає жодного посилання на годинник Windows**. Він може стрибнути, синхронізуватись, змінитись будь-як — на результат це не вплине.

### Реалізація: ~20 рядків змін у `NtpService.java`

**Що додати до полів класу:**

```java
private volatile Instant ntpAnchor = null;   // "правдивий" Instant у момент NTP-синхронізації
private volatile long anchorNanoTime = 0L;   // System.nanoTime() у той самий момент
```

**Що змінити в `startAsyncSync()` після отримання offset:**

```java
// БУЛО:
this.timeOffsetMs = offset;

// СТАЛО (додати два рядки):
long sysNowMs = System.currentTimeMillis();
this.ntpAnchor      = Instant.ofEpochMilli(sysNowMs + offset); // точний момент за NTP
this.anchorNanoTime = System.nanoTime();                        // монотонний маркер
this.timeOffsetMs   = offset;                                   // залишаємо для UI/Tooltip
```

**Що замінити в `getCorrectedTime()`:**

```java
// БУЛО:
public LocalTime getCorrectedTime() {
    LocalTime now = LocalTime.now();
    if (isSynced && timeOffsetMs != 0) {
        return now.plusNanos(timeOffsetMs * 1_000_000L);
    }
    return now;
}

// СТАЛО:
public LocalTime getCorrectedTime() {
    if (isSynced && ntpAnchor != null) {
        long elapsedNanos = System.nanoTime() - anchorNanoTime;
        return ntpAnchor
                .plusNanos(elapsedNanos)
                .atZone(ZoneId.systemDefault())
                .toLocalTime();
    }
    return LocalTime.now(); // fallback на Windows, якщо NTP недоступний
}
```

> **Аналогічно** варто оновити або додати `getCorrectedDateTime()` що повертає повний `LocalDateTime` з того самого якоря — тоді проблема опівнічного wrap-around (секція 3, пункт 5) зникає автоматично, і виконується рекомендація Codex з єдиним джерелом дати+часу.

### Щодо пропозиції Codex "NTP лише для діагностики"

Цю ідею варто розглянути як **окремий режим** у налаштуваннях, але не як основний за замовчуванням:

- У шкільному середовищі комп'ютери часто мають непоправлений годинник (мертва батарея BIOS, відключений `w32time`, ніколи не підключались до інтернету). NTP-корекція там **критична**, а не опційна.
- Якщо NTP-корекція є — вона має бути архітектурно надійною (монотонний якір), а не "найкращий зусиль" через стрибаючий Windows-час.
- Режим "лише попередження без корекції" — це добре **додатково**, але не замість правильного підходу.

### Практичний висновок

**Монотонний якір вирішує проблему в корені, а не заліплює симптоми.**

Детектори стрибків (як у секціях 4–5 та 7) — це складні евристики, які можуть хибно спрацьовувати (наприклад, на Windows з Hyper-V, під час hibernation, або на машинах із нестандартними HAL-таймерами). Монотонний якір не потребує жодних детекторів: він просто не має точки відмови для цього класу проблем.
