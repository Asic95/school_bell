# Аналіз повітряної тривоги та рівнів загрози

## Мета

Оцінити поточну реалізацію автоматичного виявлення повітряної загрози та визначити, наскільки складно додати різні звуки для різних рівнів:

- жовтий рівень — дронова загроза;
- червоний рівень — ракетна загроза.

Цей файл описує знайдену архітектуру та план можливого розширення. Зміни в коді на цьому етапі не виконуються.

## Поточний ланцюжок роботи

```text
AirAlertService
    ↓ отримує та аналізує дані API
AlertCheckResult
    ↓ містить isAlert, reason та level
SignalService
    ↓ запускає фізичний сигнал і аудіо
AudioService
    ↓ відтворює звуковий файл
ConfigService / DatabaseManager
    ↓ зберігає налаштування та шляхи до аудіо
```

## Що вже є в реалізації

### 1. Автоматичне визначення рівня вже передбачене

`AirAlertService` має клас `AlertCheckResult` з полем:

```java
public final String level;
```

Під час обробки API рівень уже зчитується з поля `alertLevel` або `alert_level`. Поточна логіка розпізнає щонайменше:

- `yellow`;
- `red`;
- `orange`.

Отже, повністю з нуля визначення рівнів створювати не потрібно.

### 2. Причина та рівень потрапляють у журнали

При першому виявленні тривоги `AirAlertService` формує причину, наприклад:

```text
Рівень: red
```

Під час уже активної тривоги сервіс також перевіряє зміни причини та записує їх у журнал.

### 3. Є окремі звуки початку та відбою

У `ConfigService` уже існують налаштування:

```text
audio.arPath       — звук початку повітряної тривоги
audio.arClearPath  — звук відбою
audio.arErrorPath  — звук помилки автоматичного API
audio.arEnabled    — увімкнення аудіо повітряної тривоги
```

Інтерфейс `SignalAudioEditorDialog` уже дозволяє налаштовувати ці звуки.

### 4. `SignalService` централізовано запускає аудіо

Метод `runAirRaidSignal()` зараз:

1. зупиняє попереднє аудіо;
2. запускає фізичний сигнал реле;
3. після завершення реле відтворює один загальний файл `audio.arPath`.

Метод `runAirRaidClearSignal()` аналогічно використовує спільний файл відбою.

## Чого зараз немає

Попри те, що `AirAlertService` уже знає `alertResult.level`, цей рівень не передається далі:

```java
signalService.runAirRaidSignal();
```

Через це `SignalService` не знає, чи була тривога жовтою, чи червоною, і завжди використовує один файл початку тривоги.

Також у `SignalService` немає окремого стану на кшталт:

```java
lastAlertLevel
```

Тому перехід активної тривоги з жовтого рівня на червоний наразі лише фіксується в журналі, але не запускає інший звук.

## Роль `DashboardQuickActionsCard`

`DashboardQuickActionsCard` відповідає за ручні кнопки:

- ручний запуск повітряної тривоги;
- ручний відбій повітряної тривоги;
- ручний запуск надзвичайної ситуації.

Цей компонент не визначає рівень загрози й не працює з відповіддю API. Тому автоматичні рівні краще реалізовувати в `AirAlertService` та `SignalService`, а не в `DashboardQuickActionsCard`.

Для ручної кнопки можна залишити загальний звук або використовувати звук червоного рівня як найбільш критичний варіант.

## Бажана модель аудіо

Мінімальний варіант:

```text
Жовтий рівень → audio.arYellowPath
Червоний рівень → audio.arRedPath
Відбій → audio.arClearPath
Помилка API → audio.arErrorPath
```

У конфігурації це можуть бути такі ключі:

```text
audio.arYellowPath
audio.arRedPath
audio.arClearPath
audio.arErrorPath
audio.arEnabled
```

Старий `audio.arPath` бажано не видаляти одразу. Його можна використовувати як fallback для сумісності зі старими налаштуваннями.

## Рекомендована поведінка

### Сценарій 1: одразу жовта тривога

API повідомляє про активну загрозу з рівнем `yellow`.

Результат:

1. запускається фізичний сигнал;
2. після нього відтворюється звук дронової загрози;
3. на дашборді відображається активна повітряна тривога.

### Сценарій 2: одразу червона тривога

API повідомляє про рівень `red`.

Результат:

1. запускається фізичний сигнал;
2. відтворюється звук ракетної загрози;
3. на дашборді відображається активна повітряна тривога.

### Сценарій 3: ескалація з жовтого до червоного

Спочатку була жовта загроза, а під час її дії API повідомив про червону.

Рекомендовано:

1. не запускати весь фізичний сигнал повторно без потреби;
2. відтворити окремий червоний/ескалаційний звук;
3. оновити збережений рівень до `red`;
4. записати зміну в журнал.

Альтернативний варіант — повторно запустити повний сигнал червоного рівня, але це може бути надто нав’язливо при нестабільних даних API.

### Сценарій 4: відбій

Для відбою можна залишити один спільний звук незалежно від того, який рівень був активним.

## Важливий технічний нюанс: пріоритет рівнів

Якщо API повертає кілька одночасних активних подій, не можна покладатися лише на перший елемент JSON.

Потрібно обирати максимальний рівень за пріоритетом:

```text
red > yellow > orange/інші
```

Інакше система теоретично може отримати одночасно жовту та червону події, але вибрати жовту тільки через порядок елементів у відповіді API.

## Орієнтовні зміни в майбутньому

Для реалізації функціоналу знадобляться зміни в таких місцях:

### `ConfigService`

Додати окремі поля, завантаження, збереження, getters і setters для звуків жовтого та червоного рівнів.

### `SignalAudioEditorDialog`

Додати два поля вибору аудіофайлів:

- звук жовтого рівня;
- звук червоного рівня.

Поточні поля відбою та помилки можна залишити без змін.

### `SignalService`

Змінити запуск приблизно до такої концепції:

```java
runAirRaidSignal(String alertLevel)
```

Метод повинен вибирати аудіофайл за рівнем і мати fallback на старий `audio.arPath`.

### `AirAlertService`

Під час першого виявлення передавати `alertResult.level` у `SignalService`.

Також бажано зберігати попередній рівень і окремо обробляти перехід:

```text
yellow → red
```

### Дашборди

Зараз усі HTML-дашборди отримують загальний тип `AIR_RAID`. Для різного кольору або тексту на екрані можна додатково передавати рівень у broadcast-повідомленні, наприклад:

```json
{
  "alertType": "AIR_RAID",
  "alertLevel": "red"
}
```

Це необов’язково для різних локальних звуків, але дозволить візуально відрізняти жовту та червону загрозу.

## Висновок

Функціонал реально додати без перебудови всієї системи. Найважливіше: визначення рівня вже частково реалізоване в `AirAlertService`, але рівень зупиняється на етапі аналізу API й не доходить до аудіопідсистеми.

Найбезпечніший перший етап:

1. додати окремі звуки жовтого та червоного рівнів;
2. передавати рівень у `SignalService` при старті тривоги;
3. зберегти старий звук як fallback;
4. залишити спільний звук відбою;
5. окремо продумати реакцію на ескалацію `yellow → red`;
6. забезпечити пріоритет червоного рівня, якщо API повертає кілька подій.

## Рекомендований вибір режиму звуків

Оскільки не кожен користувач хоче окремі звуки для дронової та ракетної загрози, не варто примусово переводити всіх на нову схему. Практичніше додати в `SignalAudioEditorDialog` вибір режиму роботи звуків.

Для двох взаємно виключних варіантів краще використати два `RadioButton` в одному `ToggleGroup`, а не звичайний незалежний checkbox.

### Режим 1: стандартний

Поточна схема для користувачів, які не потребують розподілення за рівнями:

```text
Початок тривоги → audio.arPath
Відбій          → audio.arClearPath
Помилка API     → audio.arErrorPath
```

Назва в інтерфейсі:

```text
Стандартний режим
```

### Режим 2: за рівнем загрози

Окремі звуки для різних типів небезпеки:

```text
Жовтий рівень / дронова загроза → audio.arYellowPath
Червоний рівень / ракетна загроза → audio.arRedPath
Відбій → audio.arClearPath
Помилка API → audio.arErrorPath
```

Назва в інтерфейсі:

```text
За рівнем загрози
```

## Рекомендована структура діалогу

У верхній частині діалогу слід розмістити секцію:

```text
Режим звукового сповіщення

( ) Стандартний режим
( ) За рівнем загрози
```

Поля нижче повинні змінюватися залежно від обраного режиму.

Для стандартного режиму показувати:

- Початок тривоги;
- Відбій тривоги;
- Помилка автоматичного визначення.

Для режиму за рівнем показувати:

- Дронова загроза — жовтий рівень;
- Ракетна загроза — червоний рівень;
- Відбій тривоги;
- Помилка автоматичного визначення.

Поле відбою залишається спільним для обох режимів, оскільки тип попередньої загрози не повинен впливати на базовий сигнал завершення тривоги.

## Налаштування режиму

Режим можна зберігати в базі даних окремим ключем:

```text
audio.arMode = GENERAL
```

або:

```text
audio.arMode = THREAT_LEVEL
```

Для зворотної сумісності значення за замовчуванням має бути `GENERAL`. Це означає, що після оновлення програми старі користувачі продовжать працювати за поточною схемою без повторного налаштування.

Старий параметр `audio.arPath` потрібно зберегти. Він залишатиметься основним звуком у стандартному режимі та fallback-звуком у нестандартних ситуаціях.

## Fallback-логіка

У режимі `THREAT_LEVEL` можуть виникнути ситуації, коли API не передав рівень або повернув невідоме значення. Рекомендована послідовність вибору звуку:

```text
1. Відомий yellow → audio.arYellowPath
2. Відомий red → audio.arRedPath
3. Невідомий або порожній рівень → audio.arPath
4. Відсутній і загальний файл → сигнал без додаткового аудіо
```

Так система не залишиться без звуку через неповну або змінену відповідь API.

## Поведінка ручної кнопки

`DashboardQuickActionsCard` запускає ручну тривогу без інформації про рівень загрози.

Тому в режимі `GENERAL` вона використовує `audio.arPath`.

У режимі `THREAT_LEVEL` для ручного запуску потрібно мати чітке правило. Рекомендований варіант:

```text
Ручний запуск без рівня → audio.arPath
```

Це безпечніше, ніж автоматично називати ручний запуск ракетною загрозою. За бажанням у майбутньому можна додати до ручної кнопки окреме меню вибору рівня, але це вже буде інший UI-сценарій.

## Ескалація під час активної тривоги

Якщо автоматична тривога почалася на жовтому рівні, а потім API повідомив про червоний рівень, потрібно зберігати попередній рівень окремо від причини:

```text
lastAlertLevel = yellow
```

При переході:

```text
yellow → red
```

рекомендована поведінка:

1. не запускати повний фізичний цикл повторно без необхідності;
2. відтворити червоний або окремий ескалаційний звук;
3. оновити `lastAlertLevel` на `red`;
4. записати зміну рівня в журнал.

Якщо окремого ескалаційного звуку не буде, можна повторно відтворити `audio.arRedPath`, але це потрібно захистити від багаторазових повторів через нестабільні дані API.

## Підсумкова концепція

Найпрактичніша схема виглядає так:

```text
Користувач обирає режим у SignalAudioEditorDialog
                ↓
GENERAL або THREAT_LEVEL зберігається в ConfigService/DatabaseManager
                ↓
AirAlertService визначає рівень API
                ↓
SignalService обирає відповідний звук
                ↓
AudioService відтворює файл
```

Такий підхід зберігає простий поточний режим для звичайних користувачів і додає розширений режим для тих, кому потрібно розрізняти дронову та ракетну загрози.

## Реалізований перший етап

У коді вже реалізовано базову частину цієї концепції:

- у `ConfigService` додано режим `GENERAL` / `THREAT_LEVEL`;
- додано окремі налаштування `audio.arYellowPath` і `audio.arRedPath`;
- `SignalAudioEditorDialog` отримав перемикач режиму та поля для двох рівнів;
- старий `audio.arPath` збережено для стандартного режиму та fallback;
- автоматичний `AirAlertService` передає рівень у `SignalService`;
- ручний запуск через `DashboardQuickActionsCard` і далі використовує загальний звук;
- відбій та звук помилки автоматизації залишаються спільними;
- при зміні рівня під час активної тривоги повторний фізичний сигнал поки не запускається, щоб уникнути зайвих повторів.

Наступним окремим етапом можна додати спеціальний звук ескалації `yellow → red`, якщо це буде потрібно на практиці.

## Поведінка розміру діалогу

При перемиканні зі стандартного режиму в режим за рівнем загрози з’являються два додаткові поля. Діалог має автоматично перераховувати свій layout і збільшувати висоту через `sizeToScene()`.

Рекомендована реалізація:

1. оновити видимість полів;
2. виконати перерахунок CSS та layout;
3. викликати `sizeToScene()`;
4. повторно відцентрувати діалог;
5. обмежити висоту видимою областю екрана.

Це дозволяє залишити варіант без прокрутки, але не допускає обрізання верхнього тексту або кнопок внизу. Прокручувана область залишається запасним варіантом, якщо в майбутньому кількість полів суттєво збільшиться.
